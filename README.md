# Harvest Shield

Harvest Shield is a crop-health monitoring and agricultural decision-support prototype. It combines sample field records, weather observations, CSV-based NDVI observations, preliminary risk screening, and suggested follow-up actions through a FastAPI backend and a Streamlit dashboard.

> **Prototype notice:** Field records and the checked-in NDVI observations are demonstration data. The NDVI service reads a synthetic CSV; it does not download or process live satellite imagery. Risk levels are generated by preliminary general-purpose rules and have not been validated as crop-specific predictions. Disease risk is not a diagnosis. Verify important findings in the field and consult qualified agricultural expertise.

## Current capabilities

- FastAPI endpoints for service health, field listing, field lookup, and per-field health assessments.
- Field metadata validation from `data/fields.json`.
- A weather service that can return provider, coordinate-matched cached, synthetic, or unavailable observations with source/status labels.
- A satellite-related service that reads and validates NDVI history from `data/ndvi_history.csv`; checked-in measurements are synthetic.
- Rule-based NDVI and broad weather screening with explanation messages.
- A recommendation service that maps risk assessments to cautious field-monitoring and data-collection suggestions.
- A Streamlit dashboard with Overview, Field intelligence, Risk & recommendations, and Reports & data views. It can download a fleet summary as CSV and includes clearly labelled demo fallback values when the API cannot be reached.
- Pytest coverage for field, health, recommendation, risk, satellite, and weather behavior.

## Architecture

```text
Browser
  |
  v
Streamlit dashboard (dashboard/app.py)
  |  GET /api/fields and GET /api/health/{field_id}
  v
FastAPI (backend/main.py)
  |-- Field service ---------------- data/fields.json
  |-- Weather service -------------- Open-Meteo / cached CSV / sample JSON
  |-- Satellite service ------------ data/ndvi_history.csv
  |-- Risk engine ------------------ NDVI and broad weather screening rules
  |-- Recommendation engine -------- cautious suggested actions
  v
Structured crop-health response
```

Key files:

- `backend/main.py` — FastAPI app and API routes.
- `backend/schemas/health_schema.py` — response models and data-status labels.
- `backend/services/field_service.py` — field metadata loading and validation.
- `backend/services/weather_service.py` — weather provider access and fallbacks.
- `backend/services/satellite_service.py` — CSV-based NDVI loading and validation.
- `backend/services/risk_engine.py` — preliminary explainable risk rules.
- `backend/services/recommendation_engine.py` — recommendations derived from risk assessments.
- `backend/services/health_service.py` — coordinates data services, assessment, and response creation.
- `dashboard/app.py` — Streamlit interface.
- `data/` — sample field, weather, and NDVI datasets.
- `docs/architecture.md` — architecture and limitations.
- `docs/demo_script.md` — demo steps and cautious claim guidance.
- `tests/` — automated test suite.
- `.devcontainer/devcontainer.json` — Python 3.11 development-container configuration.

## Requirements and setup

The Dev Container configuration uses Python 3.11. There is no checked-in `requirements.txt` or `pyproject.toml` in the repository root, so install the required packages explicitly.

### Windows PowerShell

Run these commands from the repository root:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install fastapi "uvicorn[standard]" streamlit pandas requests pytest httpx
```

If PowerShell prevents virtual-environment activation, use its Python directly for installation and launch commands, for example `\.venv\Scripts\python.exe -m pip install ...`.

### macOS or Linux

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install fastapi 'uvicorn[standard]' streamlit pandas requests pytest httpx
```

A live weather request requires network access to Open-Meteo. Weather requests use a short timeout and fall back to other available sources.

## Run the application

Start the backend in one terminal from the repository root:

```bash
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

Start the dashboard in a second terminal, using the same Python environment:

```powershell
$env:HARVEST_SHIELD_API_URL = "http://127.0.0.1:8000"
python -m streamlit run dashboard/app.py
```

For macOS/Linux, set the API URL with `export HARVEST_SHIELD_API_URL=http://127.0.0.1:8000` before starting Streamlit. The dashboard defaults to this local API URL if the variable is not set.

The API is available at `http://127.0.0.1:8000`; interactive API documentation is at `http://127.0.0.1:8000/docs`. Streamlit normally opens at `http://localhost:8501`. Keep both processes running while using the integrated local demo.

> A hosted dashboard cannot reach a backend at its own `127.0.0.1` or `localhost`. For separate or hosted deployments, configure `HARVEST_SHIELD_API_URL` to the backend address reachable from the dashboard environment. Deployment and secure public hosting have not been verified in this repository.

## API endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/` | Basic application information and status. |
| `GET` | `/health` | Backend process health response. |
| `GET` | `/api/fields` | List sample field records. |
| `GET` | `/api/fields/{field_id}` | Retrieve one field; unknown IDs return HTTP 404. |
| `GET` | `/api/health/{field_id}` | Return field metadata, satellite-related and weather observations, risk assessment, recommendations, timestamp, and disclaimer. Unknown IDs return HTTP 404. |

Example requests:

```bash
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/api/fields
curl http://127.0.0.1:8000/api/fields/TN001
curl http://127.0.0.1:8000/api/health/TN001
```

The health response contains `field`, `satellite`, `weather`, `risk`, `recommendations`, `generated_at`, and `disclaimer`. The backend schema currently uses names such as `ndvi_current`, `overall_risk`, and `explanation`; inspect the response from the running API rather than assuming values or a particular risk result.

## Data sources and provenance

- **Fields:** `data/fields.json` contains three demonstration records. They are not verified farms or customer data.
- **Weather:** The service attempts a live Open-Meteo request. If that fails, it may use cached CSV data only when the cached coordinates match the requested field, then labelled synthetic examples from `data/weather_sample.json`. If no valid source is available, measurements are returned as unavailable. Check `data_source` and `data_status` in each response.
- **Satellite-related observations:** `backend/services/satellite_service.py` reads `data/ndvi_history.csv`. The current observations are labelled synthetic. No live imagery acquisition or image-derived NDVI processing has been demonstrated.
- **Data status:** Responses may label data `live`, `cached`, `synthetic`, or `unavailable`. A label reports the application's source path; it is not independent proof of measurement accuracy.
- **Missing or invalid values:** Missing observations should remain unknown or unavailable. They must not be interpreted as evidence that a field is healthy.

## Risk assessment and recommendations

The risk engine is rule-based and preliminary. Its current broad screening behavior includes:

- Comparing current and previous NDVI when both values are present and within the valid range. A decrease of 0.15 or more is marked high; a decrease of 0.05 or more is marked moderate; a smaller decrease or no decrease is marked low.
- Screening weather values for broad signals: temperature below 5°C or above 40°C, relative humidity of at least 85%, and reported recent rainfall of at least 50 mm. Two or more signals produce high weather risk; one produces moderate risk. Missing or invalid measurements can leave the weather risk unknown.
- Keeping disease risk unknown because crop-specific disease observations and validated disease rules are not integrated.
- Deriving the overall risk from the available NDVI and weather indicators. If a key indicator is unknown, the overall risk may also be unknown.

These thresholds are not scientifically validated for individual crops, growth stages, or regions. The recommendation engine suggests monitoring, data verification, or field inspection; it does not prescribe treatment. An assessment is a screening aid, not a diagnosis or proof of crop damage.

## Dashboard integration status

The dashboard is present, but its current field names do not fully match the backend response schema. For example, the dashboard reads `current_ndvi`, `risk_level`, and `explanations`, while the backend schema uses `ndvi_current`, `overall_risk`, and `explanation`; the backend also returns recommendation objects. As a result, a reachable API may not populate all dashboard risk, vegetation, and recommendation views correctly. Align and verify this contract before presenting the dashboard as fully integrated.

When the backend cannot be reached because of a connection error or timeout, the dashboard can show embedded simulated demo values for the field list and selected health records. Those are illustrative UI data, not API observations. HTTP errors and invalid API responses are displayed as errors rather than treated as fresh measurements.

## Run tests

From the repository root, with the dependencies installed:

```bash
python -m pytest -q
```

Tests cover fields, health assembly, risk rules, recommendations, satellite CSV behavior, and weather provider/fallback behavior. Weather provider calls in unit tests are mocked where configured. Always record the actual output from a fresh test run on the branch being evaluated; this README does not claim that the suite has passed.

## Limitations and deployment

- This is a prototype using demonstration field records and synthetic NDVI observations.
- Live satellite image processing and crop-specific disease diagnosis are not implemented.
- Risk thresholds are preliminary and have not been validated for crops or regions.
- Dashboard-to-backend field-name compatibility needs to be aligned and tested.
- Weather availability and source depend on provider/network status and fallback data.
- A local Dev Container configuration exists, but it is not proof of a successful LinuxONE deployment.
- IBM LinuxONE access, compatibility, and deployment have not been verified here. Do not claim deployment until the target environment has been tested.
- Production security, monitoring, and operational deployment configuration are not established by the files inspected.
